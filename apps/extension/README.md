# Pluck for Chrome

The browser extension: a side panel that turns the page you are on into markdown, structured JSON, brand data, design tokens, a site map or a screenshot, through the Pluck API.

User guide: [docs/extension](https://pluck.procd.cc/docs/extension). Store listing copy and the release steps: [`store/listing.md`](store/listing.md).

## Run it locally

```bash
pnpm install
pnpm --filter @pluck/extension dev
```

Open `chrome://extensions`, turn on Developer mode, choose **Load unpacked** and pick `apps/extension/dist`. The build watches for changes; press the reload arrow on the extension card after one (the side panel reloads with it).

`dev` builds with a pinned id (`DEV_EXTENSION` in `packages/shared/src/extension.ts`), so sign-in works against a local web app without configuration: outside production the site accepts that id. Point the build at a local stack with:

```bash
PLUCK_SITE_URL=http://localhost:3000 PLUCK_API_URL=http://localhost:8080 pnpm --filter @pluck/extension dev
```

Without those it talks to the hosted service. To use an unpacked build against production, paste an API key under **Your own instance** in the extension's settings, or add the build's id to `CHROME_EXTENSION_IDS` on the web app.

To look at the UI without loading the extension at all, serve this folder (`npx serve .`) and open `store/harness/panel.html`. It runs the real bundle against canned API answers; `?scene=out` shows the signed-out state and `?theme=dark` the dark theme.

## Commands

| Command | What it does |
| --- | --- |
| `pnpm dev` | Development build into `dist/`, rebuilt on change |
| `pnpm build` | The store build into `dist/` |
| `pnpm package` | Store build, then `release/pluck-extension-<version>.zip` (reproducible) |
| `pnpm store` | Renders the store screenshots and promo tiles into `store/out/` |
| `pnpm test` | Unit tests |
| `pnpm e2e` | Loads the built extension in Chromium and checks sign-in, the page reader and the panel end to end |
| `pnpm typecheck` | TypeScript |

`store` needs Chrome or Edge on the machine. `e2e` needs a Chromium that still loads unpacked extensions from the command line: `pnpm exec playwright-core install chromium`, or set `CHROMIUM_PATH`.

## Layout

```
scripts/        build, zip, store images, end-to-end test
static/         the two HTML pages and the locale strings
src/background/ service worker: toolbar, shortcuts, menus, the sign-in callback
src/panel/      the side panel (React): one file per tool under tools/
src/options/    the settings page, which is also the welcome page after install
src/lib/        API client, sign-in (PKCE), the page reader, storage
src/ui/         shared components and the stylesheet
store/          listing copy, the screenshot scenes, the UI harness
```

Nothing about the product is typed in here twice. The build reads names, URLs, prices and the sign-in message names from `@pluck/shared` and injects them as constants (`src/lib/config.ts`), and the API types are imported from the same endpoint registry the API is built from.

## How sign-in works

Accounts are created on the site and nowhere else. The extension never handles a password or a session.

1. **Connect** generates a random verifier and state, keeps them in session storage (memory only), and opens `/extension/connect?ext=<id>&challenge=<sha256(verifier)>&state=<state>` in a tab.
2. The site checks that the extension id is one it allows, signs the person in (or up), and shows what is about to happen. On approval it stores a one-time code against the challenge and passes the code to the extension with `chrome.runtime.sendMessage`. `externally_connectable` limits who can send to the site's origin, and the service worker checks the origin again.
3. The service worker matches the state to the request it started and posts the code and the verifier to `/api/extension/token`. The site deletes the code as it reads it, checks the verifier against the challenge, and returns a new API key named after the browser.

The key never passes through the page, and a code is useless without a verifier that never left the extension. The site side lives in `apps/web/src/lib/extension.ts`.

Signing out calls `/api/extension/revoke`, so a key nobody holds stops working. A key pasted by hand (the self-hosted path) is only forgotten, never revoked.

## Permissions

The manifest is generated by `scripts/manifest.mjs`, which explains each permission. The rule: no host permissions, and nothing that shows a warning at install. The extension can see a tab only after the person invokes it there (`activeTab`), and the API is reached with ordinary CORS requests. `tabs` is optional and requested from settings.

Two consequences worth knowing when changing things:

- The page reader (`src/lib/capture.ts`) is injected with `chrome.scripting.executeScript`, which serialises the function. It must stay self-contained: no imports, no helpers outside its own body. The end-to-end test rebuilds it from its minified source to prove that.
- `chrome.sidePanel.open()` only works inside the person's own action. `src/background/index.ts` calls it before awaiting anything; keep it that way.
